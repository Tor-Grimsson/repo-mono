# 0.0.0 Documentation System Proposal

**Version:** 1.0.0
**Date:** 2025-11-03
**Status:** Proposal
**Author:** Claude

---

## Executive Summary

This document proposes a **scalable, hierarchical documentation indexing system** for the `docs/system/` directory that can grow from 40+ current documents to 1000+ without losing structure or discoverability. The system uses a **three-tier numerical hierarchy** (M.m.p-naming-convention.md), **content type separation**, and **automated cross-referencing** to maintain organization as the design system expands.

**Key Improvements:**
- 🗂️ **Infinite Scalability**: Three-level numbering supports 970,299 unique documents
- 📊 **Content Type Separation**: Research, implementation, reference, and archives are clearly categorized
- 🔗 **Automated Indexing**: Cross-references maintain themselves as docs evolve
- 📈 **Predictable Growth**: New domains can be added without disrupting existing structure
- 🏗️ **Self-Documenting**: The system documents itself with meta-guidelines

---

## Current State Analysis

### Existing System Strengths
✅ **Hierarchical numbering**: Current 0.x → 9.x structure provides basic organization
✅ **Metadata standards**: Most docs include Purpose, Status, Last Updated
✅ **Cross-references**: Many docs include "Related Documentation" sections
✅ **Rich content**: Comprehensive coverage of colors, typography, components

### Current System Limitations
❌ **Number exhaustion risk**: Limited to 0-9 for major sections (100 major docs max)
❌ **Mixed content types**: Research, implementation, and reference docs intermingled
❌ **No meta-documentation**: No guidelines for writing or maintaining docs
❌ **Inconsistent depth**: Some topics get 4 levels deep (7.1.5.1), others stay at 2
❌ **Manual cross-references**: Links break when files move or are renamed
❌ **No archive strategy**: Deprecated content clutters active documentation
❌ **Naming conflicts**: Research appears at both 6.x and 9.x levels (conflict!)
❌ **No index document**: No master list of all documentation

## Proposed System Overview

### Core Design Principles

1. **Hierarchical by Nature**: Documents exist in a tree structure, not a flat list
2. **Self-Similar at Every Level**: Each sub-directory follows the same organizational rules
3. **Content Type First**: Separate research from implementation from reference
4. **Index Everything**: Every section has an index that lists its children
5. **Version Aware**: Documents evolve, and their history is tracked
6. **Machine Readable**: Structure enables automation (indexes, links, searches)

### Numbering System

**Format:** `M.m.p-name.md` where:
- **M** (Major): Domain category (0-999)
- **m** (Minor): Sub-domain within category (0-99)
- **p** (Patch): Specific document (0-99)

**Number Allocation Strategy:**

**Major Numbers (M) - Domain Categories:**
- `0.x.x` - **Metadata** (docs about documentation itself)
- `1.x.x` - **Foundation** (architecture, setup, infrastructure)
- `2.x.x` - **Design System** (tokens, principles, guidelines)
- `3.x.x` - **Components** (atoms, molecules, organisms)
- `4.x.x` - **Pages** (templates, layouts, routes)
- `5.x.x` - **Content** (CMS, data, schemas)
- `6.x.x` - **Research** (findings, experiments, studies)
- `7.x.x` - **Operations** (workflows, processes, procedures)
- `8.x.x` - **Decisions** (ADRs, rationale, history)
- `9.x.x` - **Future** (exploration, RFCs, experimental features)

**Reserved for future expansion:**
- `10.x.x - 999.x.x` - Additional domain categories as needed

**Scale:**
- **1000 possible domains** (0-999)
- **100 sub-domains per domain** (0-99)
- **100 documents per sub-domain** (0-99)
- **Total capacity: 970,299 documents** before needing namespace expansion

## Naming Conventions

### File Names

**Format:**
```
M.m.p-[category]-[specific-topic].md
```

**Rules:**
1. **Always start with M.m.p number** (required for sorting and identification)
2. **Use lowercase** for all words
3. **Use hyphens** to separate words (kebab-case)
4. **Use category keywords** for consistency:
   - `foundation-*` for architecture docs
   - `design-system-*` for design docs
   - `components-*` for UI components
   - `research-*` for research findings
   - `operations-*` for workflows
   - `decisions-*` for ADRs
   - `future-*` for exploration
5. **Be descriptive but concise** (aim for 3-6 words after the number)
6. **No stop words** (the, and, of, etc.) unless necessary for clarity

**Examples:**
```
✅ Good:
- 2.1.0-design-system-colors.md
- 3.1.0-components-atoms.md
- 6.1.0-research-data-tables.md
- 8.1.0-decisions-architecture.md

❌ Bad:
- 2.1-colors.md (missing category keyword)
- 3.1.0-component.md (singular - should be plural)
- 6.2-type-research-findings.md (too many words)
- ADR-architecture-decisions.md (missing number prefix)
```

### Document Titles

**Format:**
```markdown
# M.m.p Category: Specific Topic Title

## Standard H1 Format
The title in the document should be human-readable with proper capitalization.

Examples:
# 2.1.0 Design System: Color System
# 6.1.0 Research: Data Table Best Practices
# 8.1.0 Decisions: Architecture - Turborepo Adoption
```

## Cross-Reference System

### Linking to Other Documents

**Always use numbered references** in cross-references, not full paths:

```markdown
## Related Documentation

**Design System:**
- [2.1.0 Color System](2.1.0-design-system-colors.md) - Color tokens and utilities
- [2.2.0 Typography](2.2.0-design-system-typography.md) - Type scales and usage

**Components:**
- [3.1.0 Atoms](3.1.0-components-atoms.md) - Button, Input, Icon components

**Research:**
- [6.1.0 Data Table Research](6.1.0-research-data-tables.md) - External best practices
```

**Cross-reference types:**

1. **Direct Reference** (doc directly related):
   `[3.1.0 Components: Atoms](3.1.0-components-atoms.md)`

2. **See Also** (tangentially related):
   `See also: [4.1.0 Pages: Home](4.1.0-pages-home.md)`

3. **Deprecation Notice** (replaced by another doc):
   `⚠️ Deprecated: See [2.2.0 Design System: Typography](2.2.0-design-system-typography.md)`

4. **Cross-Domain Reference** (different major category):
   `Related: [1.1.0 Foundation: Build System](1.1.0-foundation-build-system.md) ← Build process affects design tokens`

### Cross-Reference Metadata

**Add to frontmatter of every doc:**
```yaml
---
version: 1.0.0
date: 2025-11-03
status: active
cross-references:
  parent: 2.0.0  # What doc is this a child of?
  children:      # What docs are children of this?
    - 2.1.0
    - 2.2.0
  related:       # What docs are related?
    - 3.1.0
    - 6.1.0
  deprecated-by: []  # What doc deprecated this (if any)?
  replaces: []       # What doc does this replace (if any)?
---
```

## Growth Strategy

### Adding a New Domain (New Major Category)

**When to create:** When you have 10+ docs that don't fit existing categories.

**Process:**
1. Propose in `0.0.0-metadata-documentation-system.md` with rationale
2. Create index doc at `M.0.0-domain-overview.md`
3. Reserve major number M for the new domain
4. Start adding docs at `M.1.0`, `M.2.0`, etc.
5. Update `0.0.2-metadata-index.md` to include new domain

**Example:**
We want to add "Testing" as a new domain → Reserve `10.x.x` for Testing
- `10.0.0` - Testing: Overview
- `10.1.0` - Testing: Unit Tests
- `10.2.0` - Testing: Integration Tests
- `10.3.0` - Testing: Visual Regression Tests

### Adding a New Sub-Domain (New Minor category)

**When to create:** When you have 5+ related docs within an existing domain.

**Process:**
1. Check if existing minor numbers have room (0-99)
2. Create new minor number: `M.new.0`
3. Create index doc for sub-domain
4. Add children docs: `M.new.1`, `M.new.2`, etc.
5. Update parent index doc with new sub-domain

**Example:**
In Design System (2.x.x), we want to add Spacing:
- `2.3.0` - Design System: Spacing Overview
- `2.3.1` - Design System: Spacing Scale
- `2.3.2` - Design System: Spacing Utilities

### Adding a New Document

**Process:**
1. Determine appropriate major/minor category
2. Choose next available patch number
3. Create file with correct naming: `M.m.p-category-topic.md`
4. Add standard frontmatter with metadata
5. Create cross-references to parent, children, and related docs
6. Update index documents

**Patch Number Allocation:**
- Use next sequential number
- Don't skip numbers (use 0, 1, 2, 3... not 0, 1, 5, 10)
- If document is deleted, mark number as "retired" (don't reuse)

### Deprecation Strategy

**When to deprecate:**
- Content is outdated and replaced by new doc
- Approach is no longer recommended
- Technology is no longer used

**Deprecation Process:**
1. Add `status: deprecated` to frontmatter
2. Add deprecation notice at top:
   ```markdown
   > ⚠️ **Deprecated:** This document is outdated.
   > **Replaced by:** [2.1.0 Design System: Colors](2.1.0-design-system-colors.md)
   > **Date Deprecated:** 2025-11-03
   ```
3. Move file to `archive/` directory (preserves links)
4. Update cross-references in related docs
5. Keep file for 6 months minimum for migration period

### Version Evolution

**Semantic Versioning for Docs:**
- **Major** (X.0.0): Breaking changes, complete rewrites, major reorganizations
- **Minor** (1.X.0): New sections, significant new content
- **Patch** (1.0.X): Typo fixes, minor clarifications, link updates

**Version Update Triggers:**
- Major: Category changes, numbering changes, fundamental approach changes
- Minor: Add new sub-section, add 5+ paragraphs, add new cross-references
- Patch: Any content change that's not minor

## Benefits of This System

### 1. Infinite Scalability

**Current system:** Max 100 major docs (0-9), limited decimal expansion
**New system:** Max 970,299 docs (M.m.p with M: 0-999, m: 0-99, p: 0-99)

**Growth Examples:**
- If we add 10 docs per month, we'll hit current system limit in 10 months
- New system supports growth for 970 months (80+ years) at same rate

### 2. Content Discoverability

**Current problem:** Hard to find related docs, inconsistent organization
**New solution:** Hierarchical structure + index documents + cross-references

**Example:**
- Want to learn about colors? → Go to 2.1.x index → See all color-related docs
- Working on typography? → See 2.2.x index → Find all type-related docs
- Need research on components? → Check 6.x.x → All research in one place

### 3. Self-Documenting Growth

**Current problem:** No guidelines for adding new docs
**New solution:** System documents itself + writing guidelines + index structure

**Benefits:**
- New contributors can find guidelines at `0.0.1-metadata-writing-guidelines.md`
- When adding docs, structure is self-evident from existing examples
- Index documents prevent duplicate content

### 4. Change Management

**Current problem:** Hard to track what changed, why, and when
**New solution:** Version numbers + status field + deprecation tracking

**Benefits:**
- Version numbers make change impact clear
- Status field shows if doc is active/deprecated/archived
- Deprecation notices prevent confusion

### 5. Automation Ready

**Current problem:** Manual maintenance of indexes and links
**New solution:** Structured metadata enables automation

**Automation Opportunities:**
- Auto-generate index documents from frontmatter
- Auto-check cross-reference validity
- Auto-detect orphaned docs
- Auto-generate site maps and navigation
- Auto-create search indexes

### 6. Conflict Resolution

**Current problem:** Research docs at both 6.x and 9.x (conflict!)
**New solution:** Single source of truth for each content type

**Benefits:**
- No duplicate categories
- Clear rules for where each content type lives
- Easy to resolve conflicts by consulting guidelines

### 7. Archive Management

**Current problem:** No clear strategy for old/deprecated docs
**New solution:** Explicit archive directory + deprecation process

**Benefits:**
- Active docs stay clean and current
- Old docs preserved for historical reference
- Clear migration path for deprecated content

## Alternative Approaches Considered

### 1. Date-Based Hierarchy (YYYY/MM/name.md)

**Pros:** Natural chronological ordering, easy to add new content
**Cons:** No thematic organization, hard to find related content, poor scalability
**Verdict:** ❌ Rejected - Good for logs, bad for organized documentation

### 2. Alphabetical Organization (A/name.md, B/name.md)

**Pros:** Intuitive, easy to understand
**Cons:** No hierarchy, poor scalability, alphabetical limits (what comes after Z?)
**Verdict:** ❌ Rejected - Doesn't scale, no semantic grouping

### 3. Domain-Based Only (no numbers, just folders)

**Pros:** Natural hierarchy, unlimited depth
**Cons:** Hard to sort, no global ordering, inconsistent structure
**Verdict:** ⚠️ Partially adopted - Folders used within categories, but numbers provide global ordering

### 4. Git-Based Versioning (commit history as version control)

**Pros:** Full change history, easy to track who changed what
**Cons:** Hard to understand current state, requires Git knowledge
**Verdict:** ⚠️ Complementary - Use Git for history, version numbers for stability

### 5. Current System with Extensions (0-99 instead of 0-9)

**Pros:** Minimal change, extends current system
**Cons:** Doesn't solve content type mixing, no meta-documentation, doesn't prevent future conflicts
**Verdict:** ❌ Rejected - Doesn't address root problems

This proposed documentation system addresses all current limitations while providing a foundation for infinite growth. The three-tier hierarchical structure, content type separation, and automated cross-referencing create a maintainable, scalable, and self-documenting system.

3. **Self-documenting**: System includes its own guidelines and evolution rules
4. **Automation ready**: Structured metadata enables future tooling
5. **Migration path**: Clear plan to move from current to new system
