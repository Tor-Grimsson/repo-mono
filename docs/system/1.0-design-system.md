# Design System Overview

**Version:** 1.0  
**Last Updated:** 2025-10-16  
**Status:** Stable

## Purpose

This guide is the entry point for kolkrabbi’s shared design system. It summarizes the global conventions every app consumes and provides a map to the detailed chapters that live alongside it.

## What Lives Here

- **2.0 – Color System** → `2.0-color-system.md` covers semantic tokens, states, and utilities.
- **2.1 – Color Tables** → `2.1-color-tables.md` lists every color token/utility in quick reference tables.
- **3.0 – Typography** → `3.0-typography.md` documents the full scale and usage patterns.
- **4.0 – CSS Architecture** → `4.0-css-architecture.md` outlines Tailwind v4 layering and ownership.
- **5.0 – Styleguide** → `5.0-styleguide.md` describes how to present the system on `/styleguide`.

Follow the numeric prefixes (`n.x`) when adding new chapters so adjacent topics stay grouped. For example, future color addenda can live under `2.1-…`, typography supplements can live under `3.1-…`, and spacing or motion work can live under `6.x`.

## Core Principles

- **Semantic tokens first**: Always reach for the shared Tailwind utilities and CSS custom properties from `@kol/ui/theme.css` instead of hardcoded colors or ad-hoc styles.
- **Typography before effects**: Reuse the predefined classes from `3.0-typography.md`; avoid inventing new tracking, casing, or spacing rules without approval.
- **Light/Dark parity**: Every component must work in both themes. Tokens and utilities already handle this—use them.
- **Single source of truth**: If the design system changes, update these docs first and reference them from implementation plans or session logs.

## Naming & Layer Conventions

- **Tokens** follow the `--kol-{category}-{semantic}-{variant}` pattern (see `2.0-color-system.md`).
- **Tailwind utilities** lean on the v4 preset; do not introduce a `tailwind.config.js`.
- **Files** follow the repository conventions (`lowercase-kebab` for folders, `PascalCase.jsx` for components, etc.) outlined in `docs/RULES_STRUCTURE.md`.
- **Layering** uses the CSS cascade layers defined in `packages/ui/css/`—keep overrides scoped to the appropriate layer.

### Component Variant Naming

When creating component variants that need fixed light/dark styling (non-adaptive):

- **Use `-light` and `-dark` suffixes** for variants that maintain consistent appearance across themes
- **Example**: `.dataTablePill-light` (light background + dark text) and `.dataTablePill-dark` (dark background + light text)
- **Tokens**: Use `--surface-support-light` and `--surface-support-dark` which stay fixed across themes
- **When to use**: Status badges, pills, tags, or any component where the visual contrast should remain constant regardless of theme

**Do NOT use `-light`/`-dark` for:**
- Components that should adapt to the current theme (use semantic tokens instead)
- Interactive states (use `-hover`, `-active`, `-focus`)
- Contextual variations (use `-inverse` for theme-flipped contexts)

## How to Contribute

1. **Read** this overview plus the color and typography chapters before touching styles.
2. **Prototype** changes inside the styleguide first (`apps/web/src/routes/styleguide/`).
3. **Document** updates by editing the relevant numbered chapter and noting remaining work at the bottom.
4. **Checkpoint** the session (`docs/SESSION-LOGS/`) after significant updates so future agents inherit the context.
